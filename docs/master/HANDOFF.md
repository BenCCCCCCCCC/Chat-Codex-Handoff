## 后续产品路线

同一定位内按依赖继续推进，允许合并关联工作；每批交付一个完整的用户结果。

| 次序 | 用户结果与工作范围 |
|---|---|
| 1 · 已交付 | #39／#40 已完成补材料续学、跨来源条件、条件练习与历史证据回访。 |
| 2 · 日常可用性 | 录音／文字续接、无 AI 已保存状态、保留片段与到期提示已交付。补充物理麦克风、Explorer 双击与真实日常使用走查；当前 Windows 服务生命周期与隔离 Edge 学习分别已验证。 |
| 3 · 完整材料工作区 | 支持对已保存材料重命名、修订和移除当前使用，同时保留历史引用。评估持久保存提取正文与页／章节定位，让长材料可在后续选段继续，区分材料存储容量和单次发送预算。优先改进现有提取与来源模块。 |
| 4 · 转写迁移 | 在 2027-02-26 前完成 `whisper-1` 替换计划。先解耦模型返回、文字与时间定位能力，准备官方推荐的完成文件转写适配及准确的模型／费用记录。缺少精确时间时提供诚实的整段回听。真实服务比较与切换在具体预算批准后进行，不等待这一步才完善其余体验。 |
| 5 · 反馈质量与持续学习 | 复用已冻结协议与历史原件，补足队列之外的代表性课程材料，优先评审等义答案、材料前提、合理质疑和首要补学建议。需要付费时先形成有区分力的小规模比较和成本。将明确问题、修正和再次作答衔接成下次可继续的学习任务；工程通过率不能充当准确率或掌握度。 |

架构优化以这些结果为依据：主题应承接学习意图，材料版本用于追溯，本次任务决定发送上下文，报告保存当时证据。Codex 自行选择落实结构；全文存储／媒体读取如确有成本再调整，不要求提前整库迁移或引入向量数据库。

## 执行与验证方式

自主实现、自审、提交、推送及按既有规则合并。必要时并行独立工作，避免两个执行者同时修改同一批次。完成当前批次后，继续已明确的下一项；阻塞只停受影响部分。

沿用 `docs/TESTING.md`。对已复现缺陷验证用户结果及必要的历史关联；界面改动实际看页面。复用同一实现版本的现有 CI，不因写报告、提交文档而重复测试，不机械增加用例或规定次数。#38 已采用本机定向 + 最终 CI 集中完整验证，继续这种比例。

## GitHub 交接约定

用户希望 Chat 与 Codex 直接在 GitHub 接续工作，减少展示和人工转述。

1. 开始时读取 `meta/master-state` 的 CURRENT_STATE 与 HANDOFF，并记录所依据的 MASTER commit、产品基线和当前任务。产品 checkout 的旧副本只作指针。
2. 每个有意义批次在产品分支沿用 `docs/iterations/YYYY-MM-DD-主题.md` 写一份简洁实现／运行报告。相关 PR 可共用一份；已有报告继续更新即可。
3. 报告说明本轮实际完成的用户行为、解决与仍存在的问题、必要取舍、实际执行及复用的验证、未验证内容、对应代码版本／PR／CI、接续任务和阻塞。失败与未解决事项留在记录里。字段可按内容合并，不补空表，不复制全项目历史。
4. 完成推送／合并后，把准确版本、报告和 CI 链接回写 CURRENT_STATE；HANDOFF 保留接下来要执行的内容。更新前核对远端最新状态，保留并发的新决定，不用过期副本覆盖。
5. Chat 审查本轮变化与证据，反馈分 Must Fix / User Decision Needed / Future Optional，并直接写回 MASTER。能自行修复的继续推进；向用户只报告有意义的进展或需决策的事项。

GitHub 只保存允许公开的代码、合成案例、脱敏结论及适量必要证据；学习者原件保留既有私有位置。发布报告、排队、执行中、已合并分别按实际状态记录；无执行回执时不写“已完成”。交接文档本身不证明已启动桌面 Codex。

## 反馈分类与决定边界

**Must Fix**：#39 所列条件不可用与补材料中断已解决。继续修实际日常使用阻塞，并按期限推进转写维护；材料版本管理是下一批明确方向。

**User Decision Needed**：目前没有阻止当前批次实施的产品决定。真实付费调用、个人录音研究／原件外传、七天保留政策变化、大规模迁移、公开部署或产品定位扩展，形成具体方案后集中提交用户决定。

**Future Optional**：独立模型复核、向量检索、整库媒体优化、云同步、多 Agent 产品形态。按实际需求和证据安排。
