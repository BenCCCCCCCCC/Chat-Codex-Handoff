# R1 产品定义、四层方案与评测协议

版本：0.2 / 2026-09-09  
类型：MASTER 设计决策；除明确引证外，均是待验证设计，不是已实现功能。  
依赖：R1_RESEARCH.md；来源索引 SOURCES_AND_DECISIONS.json。

## 1. 一句话产品定义

**单次 Web 变更的可追溯验收单**：把已批准条件、对应版本证据、不能证明的事项与评审建议集中呈现，让非工程产品负责人少找材料、少作错误接受/返工决定。

工作名不是新品牌或仓库更名。先嵌入现有工具，独立软件形态须由采用证据证明。

## 2. 四层分别回答什么

| 层级 | 当前方案 | 最重要的否证问题 |
|---|---|---|
| 用户层 | 实际负责简单 Web 演示/原型交付验收、重复有变更的 PM/运营/小团队 owner | 是否真的遇到跨工件/版本混乱？现有方案是否已经够省事？ |
| 产品层 | 面向一项变更的一页验收单；先给结论边界，再给可展开证据 | 是否帮助作出正确决定，而不是增加另一份要阅读的文档？ |
| MVP 层 | 一仓库、一类低风险 Web 变更、已确认条件、一个执行工具、逐条建议与一次有限返工 | 相比原生工具+规格/报告，增益是否大于设置与阅读成本？ |
| 可实现层 | 复用 runner/规格工具；结构化工件；规则检查来源；模型解释语义；人批准 | 是否能取得真实对应版本证据，且没有额外高风险接入/成本？ |

## 3. 用户问题与使用旅程

### 原有旅程

确认需求 → AI 宣称完成 → 寻找截图/日志/版本 → 把材料搬给另一处评审 → 再补材料 → 判断接受或返工。

来源：本项目 owner 的单用户经历，不推广为所有 PM 的常态。新目标用户旅程需由访谈/任务观察确认。

### 候选旅程

owner 确认一组有编号的验收条件；建造者完成任务并生成一次工件快照；验收者打开一页报告，逐条看“证据够不够/建议如何/仍需人判断”，接受或只回传明确缺口。不要求 owner 再学 shell、查 Git 或阅读整仓源码。

产品输入不能只靠 AI 从已实现代码反推需求。原需求发生改变时生成新 requirement_revision，旧决定保留为旧版本决定。

### 为什么不是一张自动盖章的测试报告

三层状态必须独立：

- **来源与完整性**：VALID / INVALID / UNKNOWN。文件哈希匹配仅证明与快照一致，不证明其生成者可信或测试真实运行。
- **条件判断**：SATISFIED / NOT_SATISFIED / INSUFFICIENT_EVIDENCE / NOT_REVIEWED。来源/适用性不足不能支持正向满足建议，但材料不够不等于功能一定失败。
- **人的决定**：PENDING / ACCEPTED / REJECTED / ACCEPTED_WITH_LIMITS。默认 PENDING；不得由规则或模型擅自代写接受。

命令 exit=0 只支持该命令/断言的结果，不支持全需求通过。截图可以证明某个显示状态，不能自动证明持久化、无新 tab、权限或副作用都正确。Demo 与真实执行必须区分。

## 4. 最小界面信息架构

顶部：任务名称、目标版本的易读摘要、尚未审阅/材料不足的数量，明确“未作最终批准”。

主体：每条条件一行，显示要求、评审建议、证据依据、为什么不足/如何补齐。先显示人能理解的内容；完整 SHA、hash、来源路径放详情。

底部：明确需要产品决定的事项、范围内修正项、以后可选项。P0 输出静态 HTML/JSON，不假做可点击但不能持久化的接受按钮。后续 MVP 才实现有效的 owner 决定记录。

P0 不新建聊天框，不强制打开 ChatGPT 网页，不模拟粘贴。报告由 owner 显式打开；现有 Chat/Desktop 可以保留为沟通入口而不是产品必须控制的宿主。

## 5. 功能优先级与非目标

### P0：本次开发建议，先验证资料可靠与报告可读

- 显式条件与证据输入契约；读取已有 R0 支持材料。
- 按 run_id 冻结一次工件，保留缺失/混合版本，拒绝无声覆盖。
- 检查引用存在、哈希、声明的版本适用性，输出可解释结果。
- 同材料生成 A 原始资料索引与 C 条件式报告，便于后续公平对照。
- 接受可选的结构化评审建议作为数据；缺少建议显示 NOT_REVIEWED，不假装运行模型。
- 一份本地 HTML 验收单、JSON 结果及一个可转交的最小审查包。

### MVP：后续需另行批准的完整小闭环

复用一个实际可用的既有执行工具，处理一个真实低风险 Web 任务；由 owner 确认条件；生成版本绑定证据；单个模型提出带证据引用的判断；用户接受或要求一次明确返工；保留完整效果/成本/人工负担记录。

MVP 不能只靠六个 helper 自修案例验收。没有新目标任务和用户观察，不宣称需求/商业成立。

### 不做

通用 QA 平台、IDE、多 Agent 编排、多模型商用服务、账户计费、生产部署、自动发布、自动 approve、客户端内部接管、Desktop deep link、浏览器标签管理、零闪窗、为好看而全面重写 GUI。RAG/微调不属于默认需求。

## 6. 技术选择与迁移

P0 建议使用已验证可用的 Windows PowerShell 5.1 与系统库生成静态报告，不安装新依赖。新模块与 legacy 目录分离；JSON 契约避免绑定 WinForms，跨平台改写只有真实采用要求出现才做。旧工具、分支、历史原地保留。

需要复用：Git 只读版本事实、既有任务工件、原生 JSON/HTML/trace 报告能力。Playwright 的 captureGitInfo 和 reporter 已存在，不自称发明版本绑定。[C07,C08]

将来模型接入优先考察既有 Codex 的非交互结构化输出；本机兼容性、配额、权限、失败/取消语义仍须专门实验。[T01] 单进程/单任务足够时，不引入完整 app-server/服务。

原则：内容是数据，不是可执行命令。禁止从报告加载并执行脚本/URL；路径白名单、输入规模限制、HTML 转义、无远程依赖、无 credentials、无自动外发。审查包只含被明确选择的材料，不能递归打包整个 repo 或 `.git`。

## 7. 评测与数据协议

### 样本分层

A. **既有真实材料**：R0 报告的 6 个案例，Codex 再读当地原件确认逐条来源。只作探索，不伪称目标用户样本；+1 当前归属问题单独列为 observation。

B. **工程 fixture**：缺文件、错hash、版本冲突、未评审等边界。明确 synthetic，只证明程序规则；不能变成真实市场任务。

C. **后续真实 Web 任务**：未来经授权取得，冻结任务与需求时点，形成开发集/保留集。原项目功能类型相同的变体不能跨集泄漏。

D. **人工标签**：依据在当时可获得的证据，由 owner/合适独立评审者标注；历史 MASTER 判定不是自动 ground truth。分歧保留，不为了高分删除困难样本。

禁止为过去日志补写“当时 HEAD”来消除 Unknown；可另建回顾性标签，但记录 author、时间和 source，不能当作当时的独立原始证据。

### 对照基线

- **A**：原生 Codex/现有报告 + 一份合理模板；不是没有提示、没有资料的弱对照。
- **B**：固定版本的 OpenSpec 或 Spec Kit + 现有测试报告；启用其本来就有的需求/场景核对、版本元数据等能力。
- **C**：相同材料与模型预算，在 B/A 上增加候选报告模块。

P0 仅准备资料与展示对照，不安装/运行竞品、不额外调用模型。后续正式比较时保持同一任务材料、时间截面和评审预算；顺序随机/交叉，记录学习效应。用同一题先读答案再做下一种不算公平测试。[T02,U03]

### 指标定义

| 指标 | 分母与算法 | 防止的误用 |
|---|---|---|
| 错误放行率 | 无充分支持的 SATISFIED / 所有建议 SATISFIED | 另报数量与小样本区间，不能因 0 个就宣称安全 |
| 漏阻断率 | 被建议 SATISFIED 的真实失败/不足条件 / 全部人工标为失败/不足条件 | 与错误放行率分母不同，均应保留 |
| 不必要否定率 | 人工确认满足却被 NOT_SATISFIED / 人工确认满足条件 | INSUFFICIENT 单独分析，不混入“代码有 bug” |
| 有效判断覆盖 | 可用明确建议数 / 可判定条件数 | 全部回答 Unknown 不能靠低错误率获胜 |
| 引用有效率 | 能定位且适用于该条件/版本的引用数 / 全部引用数 | hash一致不等于语义适用 |
| 端到端人工负担 | 设置+资料准备+查阅+补件+决定+返工的人类主动分钟 | 同时报日历耗时；并行任务不双计为效率提升 |
| 补件/无必要返工 | 由材料问题产生的回合数、误返工项数 | 不把真正范围改变算模型失败 |
| 成本与重复采用 | 每有效验收的实际资源/人工成本；下次自愿采用/绕开 | 不用试用点赞推断付款意愿 |

### 决策阈值（设计值，未测结果）

工程硬约束：所有已定义安全 fixture 中，失配/缺失材料不能被升级为已满足或 owner 已接受；原材料不被改动。发现此类错误立即停止产品演示进入修复。

产品比较初始目标：在不增加错误放行/无必要否定的条件下，相比最强现成基线，人工主动处理时间有实质下降（试验预设可用 20% 作为讨论阈值），且没有只靠多弃答换分数。小样本只作方向信号，不宣称统计胜利。

若原生配置或模板达到相同结果、C增加设置/阅读负担、或找不到重复责任场景，则收敛为扩展/模板或停止；不因已经写了代码继续加功能。

## 8. 用户研究准备（协议已完成；执行为 0）

招募条件：近期实际用 AI/建造者交付过简单 Web 变更、本人参与验收、能够展示去敏材料。首轮可控制在 3–5 位以发现问题，不作为统计代表性样本；无可访问用户时不虚构。

一次访谈约 25 分钟：回顾最近任务；展示如何判断完成；询问一次误判/补材料；看到候选验收单后完成一个实际判断；询问不用本工具会怎么做。不要先讲“会省时间”，不要用“愿意用吗”代替实际行为。录音、真实材料共享、联系他人都需授权。

收集字段：角色/责任、任务频率、当前替代工具、真实例子、补材料和决策步骤、偏好及放弃原因。报告合并角色计数、任务数、可验证材料数，不把同一人多次体验当不同用户。

付款探索先观察替代成本和重复使用，后续再做明确的付费试点；P0不收费、不建立支付模块。

## 9. 校招能力映射与可讲述成果

| 能力 | 这阶段本人应承担的决定 | 可展示证据 | 不能声称 |
|---|---|---|---|
| 问题定义 | 从“少粘贴”改为“正确验收的总成本” | 问题树、用户筛选、否证记录 | 访谈已完成/需求已普适 |
| 竞品/战略 | 放弃重复测试引擎，选择组合/扩展 | 固定来源矩阵、build-versus-reuse | 无竞品、独创类别 |
| AI适用性 | 规则/语义/人判断边界 | 失败状态与交互方案 | 用了很多Agent就更好 |
| 产品与交互 | 先显示待决定事项，再展示技术证据 | 短PRD、验收单、可用性观察 | GUI漂亮代表用户接受 |
| 技术落地 | 输入输出、版本和权限契约 | 原型与真实测试/环境约束 | Codex写代码=本人手写全部工程 |
| 评测与迭代 | 定义误放行、无必要返工和人工成本 | 标签协议、对照、BadCase/结果 | 软件测试数量=模型质量或业务提升 |
| 商业判断 | 何时只做模板、何时才独立化 | 成本/采用假设与退出门槛 | 用户、营收、增长率的虚构成绩 |

与训练的“知道/做过/能独立做/能排错”逐项对应，不因文档写了就自动升级能力等级。亲自能解释取舍、复现失败、解释迭代依据比增加术语重要。职位描述是参考，不承诺特定公司录用。

## 10. 最终边界

这是一份可实施、可失败、可退出的产品方案。研究结论不是“必须做大”。下一步仅提议 R1-BUILD-01 开发包；完成它后，MASTER 应先看是否值得进入实际模型/用户闭环，不自动批准后续阶段。
