# DIRECTION-DEEPENING-01 v4 — 学习→口头讲解→诊断→再学习的连续产品流

日期：2026-09-10
角色：00 MASTER
状态：ACTIVE PRODUCT / ENGINEERING DESIGN；未启动本机开发、录音、模型/API、安装或付费执行

## 1. 最新纠正

Owner指出上一版“确认评价要求 -> 用户录音/上传”过于僵硬。正确产品体验应更接近Study Mode：**先帮助用户真正学会，再自然进入“我来讲讲”的费曼式口头输出；录音是产品本身的核心能力，不要求用户事先录好再上传。**

因此v4替代v3的交互主流程，但保留v3的双通道音频/文本架构、错误归因、PTE式分维度而非照搬分数、原音频证据、ASR错误保护及Chat替代性Gate。v3详细来源/竞品研究保留在Git历史；本文件是当前产品流和研发基线。

这不是把Study Mode复制一遍再加麦克风。普通讲解、反问、测验本来就可由Chat完成；候选产品新增的是**从教学上下文无缝进入一段由本产品直接录制的独立讲解，并对原声、转写、知识/逻辑与表达进行可回听的分层诊断，再自动回到针对性教学与重讲。**

## 2. 核心产品循环

当前主循环改为：

`学习 Learn -> 我来讲 Explain -> 证据诊断 Diagnose -> 针对性再学 Repair -> 再讲 Re-explain -> 新情境 Apply`

不是线性考试表单。用户可以在“学习”和“讲解”之间来回切换；产品内部保持同一学习主题、来源、尝试与反馈状态。

### 2.1 Learn — 先教会，而不是先发评分标准

用户从熟悉入口开始：输入主题、粘贴一段材料或选择有限学习资料。产品先像学习导师一样：
- 问用户目前知道什么、哪里卡住；
- 分层解释，不默认一次给完标准答案；
- 用问题、例子、反例、小练习检查理解；
- 用户明确要直接解释时直接解释，不强制苏格拉底流程；
- 对来源型学习，回答与解释尽量锚定用户材料；开放事实若引入外部知识，要与来源内容区分。

后台可从材料和学习目标生成内部 `learning_anchors`（核心概念、关系、条件、易混点），用于后续检查；**用户正常流程不需要进入“确认评价要求”页面。**

用户前台只看到简短的“本轮学习重点”，例如2–4条普通语言目标。若材料本身有冲突、目标太宽或评判条件不清，Tutor在对话中自然追问；只有真正歧义影响评价时才要求用户确认。

内部标准必须版本化并绑定来源，不能在用户讲完后为了让结果更好看而暗改。技术上的criteria仍存在，但它是后台保证公平性的合同，不是用户必须操作的表单。

### 2.2 自然切换 — “我来讲讲”始终可用

“讲给我听 / 我来讲讲”是学习界面的一级操作，始终可用，不等Tutor宣布“你已经学会”。

Tutor可在合适时自然建议：“你已经能说明A和B了，要不要现在用自己的话讲一遍？”用户也可以随时主动进入讲解模式；觉得没准备好则继续学习，不产生失败标签。

进入讲解前只选择必要的辅助级别：
- 无提示；
- 只看关键词；
- 允许查看学习材料。

辅助级别写入本次attempt，用于解释结果；它不是作弊检测。默认不展示完整内部anchor或标准答案，避免把口头输出变成照读rubric。

### 2.3 Explain — 产品自己录音，不要求上传

v0.1的主路径是**产品内直接录制**。Web/PWA候选可使用浏览器麦克风权限与MediaRecorder一类标准接口；用户点击一次开始，界面显示计时、录音状态与简洁波形/音量反馈。

第一版独立讲解优先使用连续录音：开始 -> 讲 -> 结束。不给普通“暂停后继续”作为默认操作，因为人为暂停会破坏自然停顿测量；设备中断或未来支持的显式暂停必须记录为capture metadata，并从自然停顿统计中排除。

用户可以结束后重录。系统不在独立讲解过程中实时打断、自动补句或显示完整答案。

“上传已有录音”从普通用户主流程删除。它最多保留为开发/测试/无麦克风情况下的受控备用入口，不能让产品体验依赖用户先到别处录音、保存文件、再上传。

如果学习阶段允许语音提问，要区分两种麦克风行为：
- **对话语音输入**：用于和Tutor说话，不进入正式attempt评分；
- **讲解录音模式**：明确开始一次attempt，保存原声并进入完整分析。

不能把用户随口问问题的一段语音错误当作“口头讲解表现”。

## 3. 录完后的双通道架构保留

每次正式attempt只保存一份原始录音作为主证据，再并行派生：

A. **Audio observation channel**：解码/质量检查、语音活动估计、可观测内部静音/停顿候选、总时长、有效说话时长、速度等；原始测量与解释分开。

B. **Transcript channel**：忠实ASR、必要的句/词时间对齐、关键否定/数字/条件/专业词风险、原始转写与用户纠正版本。

两条在原始音频时间轴上对齐后再分成：

C1. **Content/logic assessor**：只看来源、learning anchors和可靠转写/用户原话，不先看“流利度差、停顿多”等提示，避免把口头风格偷渡进知识判断。

C2. **Delivery interpreter**：看原话、可验证的音频事件与上下文，解释哪些位置可能影响表达清晰度；不能把停顿、口音、填充词或自我修正直接解释成不会、紧张、智力或人格问题。

最终report由程序合并和校验。模型不能发明停顿时长、时间位置、source引用或把“相关”改成“因果”。

## 4. Diagnose — 反馈直接进入学习，而不是另开评分报告

用户讲完后首先看到少量优先反馈，不是PTE式总分面板：

1. **你讲对/讲出的内容**：哪些核心关系已在本次表达出现，指向原话和来源；
2. **最值得补的一处知识/逻辑**：缺失、方向错误、条件不完整、例子不支持或指代不清；
3. **一处口头表达观察**：只有在有可核对声音事件时展示，例如某个关键条件之间存在较长停顿、重复修正；它与知识判断分开。

每条重要反馈必须能点回原声时间段和对应转写。关键ASR词不确定时，先让用户回听并快速纠正，之后重新计算受影响的文本/语义结果；修改转写不能修改原音频事实，也不能算成口语进步。

“没讲到”显示为“本次尚未表达/尚未证明”，不等于永久不会。存在合理替代表述、来源不足或模型/工具冲突时保留Unknown/需确认。

## 5. Repair — 产品自动回到针对性教学

反馈页不是终点。点击一个内容/逻辑问题后，Tutor回到学习状态，只针对该缺口帮助用户：
- 用追问让用户补关系；
- 换一个例子确认；
- 必要时重新解释这一小点；
- 不自动把整篇标准答案写出来要求用户朗读。

表达问题则给可执行的小练习，例如“把这两个条件合成一句完整规则再说一次”，而不是人格化评价。

用户可以选择：
- “再讲这一段”：录一段新的局部attempt，旧录音保留；
- “重新完整讲”：新建完整attempt；
- “我先继续学”：回到Tutor。

这使Study与Teach-back成为一个循环，而不是“学习App + 评分网站”两个拼起来的系统。

## 6. Apply — 新情境才承担有限的迁移检查

同题重讲改善只说明用户在获得反馈后能修正本题。若要观察是否会用，提供一个内容不同但要求相同概念/关系的新情境。

Apply可以先用文字回答，也可以再次录音；首版不强制所有环节都用语音。记录本次是否使用提示/看材料，避免把有提示答案和独立表现混为一个“掌握度”。

不根据一次应用题得出长期掌握、考试预测或真实工作能力结论。延迟保持、学习收益、留存需要以后单独研究。

## 7. 更新后的四层产品定义

### 用户/场景

首批仍是假设中的成年学习者：刚学完一份有限材料，近期需要真正理解并能用自己的话解释一个概念/规则/机制。普通话、单人、低风险。AI轻用户是低学习门槛要求，不是低专业能力。

真正打开理由：**“先帮我学懂；等我觉得差不多，我讲给你听，告诉我哪一句还没讲清。”**

### 产品

不是“录音打分器”。它是一体化的**学习导师 + 口头teach-back工作台**：教学上下文、正式录音、原声证据、分层诊断、针对性再教和重讲共享同一状态。

主要价值假设：从“我看懂了/AI说我懂了”转成可复听的自我解释证据，并让反馈直接回到下一步学习。该价值尚未通过用户比较验证。

### MVP / v0.1

一个Web/PWA表面；一种有限来源/概念类材料；普通话；文字Tutor为主，用户可打字或普通语音问问题；正式“我来讲”使用产品内麦克风连续录音；录完批处理；原声回听、忠实转写、双通道分析、少量反馈、局部/完整重讲、一个新情境、历史与删除。

不做实时全双工语音老师、全学科知识库、知识图谱社交、PTE模拟认证、英语发音等级、实时打断、多人课堂或原生多端App。

### 可实现性

浏览器Web可直接请求麦克风并录制MediaStream，实际部署需HTTPS/权限/浏览器兼容检查。音频处理继续复用成熟VAD/ASR/对齐/播放器组件；语义模型做来源约束的内容/逻辑解释。无需训练新的基础模型。

主要难点不是录音按钮，而是：ASR忠实度、时间对齐、指标校准、知识/表达解耦、错误归因、数据留存/删除、模型费用与实际延迟。

## 8. 为什么不直接使用ChatGPT Study Mode / Voice

当前Study Mode已经会逐步解释、提问、根据上传材料检查理解，因此**Learn部分本身不是我们的创新，应把它当强基线和可借鉴交互。**

如果产品只做到“Study Mode + 按麦克风 + AI点评”，仍然没有开发必要。

候选增量是：
- 产品拥有一次正式attempt的原始录音，而不是只依赖聊天转写；
- 声音事件、ASR文本、用户纠正文本、来源和反馈可版本化并互相定位；
- 内容判断与表达观察隔离；
- 每条负面反馈可回听证据并识别ASR/工具错误；
- 再学习与重讲共享同一缺口状态；
- 同题修正与新情境应用分开记录。

Chat/Skill若通过合法工具能提供相同原始音频、时间线、可追溯反馈和状态循环，而且用户负担更低，则正确形态可以是ChatGPT Plugin/App；不要为了“独立产品”重造聊天界面。当前未确认Chat插件是否能直接获得宿主Voice原始音频，因此首个可控工程面优先考虑自有Web录音组件。

## 9. UI不再是四个僵硬页面

建议一个主学习界面＋两个辅助视图：

**主学习页**：Tutor对话/学习材料/简短学习重点；底部一直有“我来讲讲”。点击后同页进入录音状态，结束后反馈卡回到同一学习流。

**讲解详情抽屉/页**：波形、转写、反馈锚点、回听和局部重录。默认不让技术指标占满主屏。

**历史/数据页**：按主题查看attempt、辅助级别、重讲记录，导出或删除。不是排行榜或统一能力分。

没有单独“确认评价要求”页面，也没有“请上传你的录音”作为标准路径。

## 10. 研发顺序修正

后续工程包应按用户真实旅程构建，而不是先做一个孤立音频分析器：

A. Tutor/材料/学习状态 + 可自然进入的录音模式；
B. 产品内麦克风采集、原声保存/播放/时间基准与失败恢复；
C. 双通道音频/ASR/对齐与数据质量门禁；
D. 分离的内容/逻辑与表达分析、反馈锚点；
E. targeted Repair -> re-record -> Apply -> 历史/删除完整整合；
F. 工程自测、语音误判/ASR关键错误挑战样本与一次综合owner walkthrough。

内部测试仍必须随研发进行，尤其要覆盖：内容正确但有停顿、流利但错误、关键否定ASR错、用户纠正转写、设备中断、来源变化、局部重录与完整重录区分。长期学习效果/真实用户留存可在功能版之后研究。

## 11. 当前状态

Completed：根据owner修正重新设计主流程；Study-first、always-available teach-back、产品内录音、后台criteria、反馈回到学习的闭环已定义；双通道技术基线与Chat替代性Gate保留。

Verified：当前官方Study Mode确实支持逐步解释、苏格拉底式提问、上传材料与理解检查；浏览器MediaDevices/MediaRecorder可在取得权限的安全上下文中录制麦克风。此前ASR/VAD/竞品源码与PTE边界保持原证据级别。没有新本机运行。

Likely：学习和讲解无缝切换比“确认评分要求->上传录音”更符合普通学习体验；这是产品设计判断，不是用户研究结果。

Unknown：实际Tutor到teach-back转化体验、普通话ASR/对齐/反馈准确度、Chat Plugin原音频权限、延迟/成本、用户复用和学习迁移。

Not Done：Codex本地实现、真实录音链路、模型/API验证、用户试用、竞品实跑、发布。

Must Fix：旧开发规格中任何“普通用户上传录音”“确认criteria后才能录”“先考试再教学”的主流程不得继续作为默认实现。

User Decision Needed：当前普通产品设计无需；真正开发范围、安装/API/语音数据处理/费用/发布等仍在相应Gate处理。

Future Optional：实时AI语音Tutor、英语/PTE发音、移动原生App、完整知识图谱、多人学习；不在首版。
